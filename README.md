# Pitwall

A local dashboard for running many Claude Code sessions in git worktrees. macOS only.

- **Repos**: add a repository, or a folder to scan for repositories and worktrees (up to 5 levels deep, rescanned every 30 s). Removing a repo hides it from later scans.
- **Sessions run out of sight**: a Claude started from Pitwall runs in a detached tmux session (own socket `pitwall`, config `config/tmux.conf`, never your `~/.tmux.conf`), so no terminal window exists until you want one. **Terminal** (in the `⋯` menu) opens a Ghostty tab attached to it, or switches to the tab already attached; closing that tab only detaches, and Claude keeps running. The tmux sessions outlive Pitwall restarts and end when Claude quits. Every interactive Claude Code process in a tracked repo shows up on the board, whether you started it by hand or from the app. The app finds them through `~/.claude/sessions/<pid>.json`, which also carries Claude's live status (working, your turn, waiting for a permission prompt), and drives each one by its tty: tmux `paste-buffer` and `send-keys` into Claude's own pane for a hidden one (a split or window you open in it gets none of it), Ghostty's AppleScript for one you started by hand in a Ghostty tab. Right before each paste and again before its Enter, the board checks that the terminal still runs that very Claude (same process, same conversation, in front of its terminal, not showing a permission prompt the text would answer); when not, nothing more is typed: a send stopped before its paste typed nothing, and one stopped before its Enter leaves its text typed but unsent in the terminal, which its error says. Without tmux installed, sessions open in Ghostty tabs instead.
- **Worktrees**: **New task** (N, or the top bar's button: a dialog over the Wall or a task page) asks for the prompt first, then the repository (its picker filters by name or path as you type; a letter on the closed picker starts the filter) and a name (a space typed in it becomes a hyphen), and ⌘↵ creates the worktree, starts Claude there with the prompt and opens its page. Worktrees are created and removed by [`scripts/git-wt`](scripts/git-wt), also usable as `git wt` once linked into `PATH` (`ln -s $PWD/scripts/git-wt ~/.local/bin/`). A task's worktrees sit at `<repo's parent>/worktrees/<task>/<repo folder>` (root overridable per repo), so one task name can span sibling repos and `../<sibling>` paths keep working. A new worktree first asks origin for its default branch and fetches it, so a new branch starts from origin's latest state: from `origin/<branch>` if that exists, else from origin's default branch, whatever its name (overridable per repo; an override also starts from origin's copy when origin has one). If origin cannot be reached the task is refused with that error rather than started from a stale state; a repository with no origin starts from its main checkout's branch. Files matched by the main checkout's `.worktreeinclude` are copied in. A task that needs no worktree of its own picks **Existing branch, no worktree** in New task instead: you only pick one of the repository's local or remote branches (the task is named by Claude's generated title, the branch until then), and Claude runs where that branch is already checked out, or else in the main checkout switched to it (refused while a Claude runs there or it has uncommitted changes; a remote-only branch gets a local tracking branch). The setup command does not run then. Each worktree lists its Claude Code conversations from `~/.claude/projects`: **New Claude** and **Continue** start `claude` in a hidden tmux session (the setup command runs first in a new worktree); **Terminal** shows a running one.
- **A task across a folder of repos**: a folder that holds two or more of your repositories (say `~/code` with `web` and `api`) is listed in New task's picker above the repositories. Picked, it takes a prompt and a name only: Claude starts in an empty task folder `<folder>/worktrees/<name>`, reads the repositories' main checkouts (it is allowed to read the whole folder and told never to change a main checkout) and decides which ones the task needs. Before changing one it calls the `open_worktree` tool, which creates the worktree `<task folder>/<repo>` on the branch `<name>` with `git wt` (or returns the one that exists) and hands back that repository's setup command for Claude to run there. A Claude you start yourself in a task folder, or resume there, gets the same. The task's facts list its worktrees as they come; its Diff is one patch over all of them, each file under its repository's folder; **Clear task** names what each worktree would lose, then removes every worktree with its branch (long-lived ones kept) and the task folder. Repositories' `.claude/settings.json`, agents, commands and `.mcp.json` do not load from a task folder (Claude Code reads them from its working directory); their CLAUDE.md and skills load once Claude touches a file in the repository.
- **Scheduled tasks**: under **More**, New task's **Start** is **Now** by default; **Once** takes a date and time to come, **Repeat** a time of day and the weekdays to run on (weekdays at 09:00 to begin with). A scheduled task needs a prompt, and the main button reads **Schedule**. The schedule keeps everything New task would have started with (the repository or folder, a new worktree or the current checkout, branch, worktree path, prompt, model and effort) and starts that task when it comes due, just as ⌘↵ would have; each run of a repeating one gets a worktree and a name of its own, the schedule's name and the date (`nightly-review-2026-11-03`, `-2` on a clash). Pitwall looks at the start of every minute, as schedules are set in whole minutes; a run that came due while the Mac slept or Pitwall was not running starts once when it is back, however many it missed, and the task's facts say it was due earlier and started late. The Wall lists the schedules under **Scheduled**, after the tiles, and its heading counts them with the next run as a link down to them; each shows where and when it runs, its prompt, the next run (**Paused**, or **Done** for a one-off that ran) and the last one (a link to its task, or why it failed to start, say uncommitted changes in the main checkout), with **Run now**, **Pause**/**Resume** (a repeating schedule resumes at its next time, skipping the runs it was paused through) and Delete (with Undo). A task a schedule started names it under **Schedule** in its facts.
- **Diff**: one patch per worktree against the merge-base with `origin/<base branch>` (the local base branch only when origin has none), including committed, staged, unstaged and untracked changes, as of your last fetch. Your index is never touched. The Diff tab lists every changed file with a few lines of context in one scrolling view, a line too long for its side wrapped; clicking a folder in the tree on the left shows only its files, and clicking a file opens it alone, in full, at its first change (**← All files**, **All files** atop the tree or Esc goes back), and J and K step from file to file. The **+** beside a line number, clicked or dragged down over lines, opens a box under them to write a draft about those lines: Enter (or **Keep for later**) keeps it under Later, **Send when it's my turn** arms it, Esc drops it, and nothing reaches Claude from the diff. The draft keeps the file, the line numbers and their code (up to 40 lines), shows them above its text under Later (a click on the file and lines opens the Diff at them, marked, or says the file has no changes any more), and goes to Claude with them in front: ``About `server/git.ts` lines 89–91:`` followed by the code in a fence, then the draft.
- **Attention is contextual**: `pnpm claude:connect` registers the `ask_human` MCP server at user scope (`http://127.0.0.1:7420/mcp`) and allows its tools (`ask_human`, `ask_questions`, `create_artifact`, `open_worktree`) in `~/.claude/settings.json`, so every Claude session has it (running ones after a restart or `/mcp` reconnect). The app reads the call from the session transcript and shows it as a decision on the task's page, and your answer is typed into the session's terminal as the next prompt. `pnpm claude:disconnect` undoes the registration and removes the hooks.
- **Wall and task page**: the **Wall** (`/`, and `/wall` too) has every task as a tile, in the order of attention: decisions (`ask_human` calls, rounds of questions and Claude Code's menus), then Needs focus (a prompt only the terminal can answer), then Your turn (Claude finished and waits for your next message), each kind with the one that has waited longest first (a decision since it was asked, any other since its task last changed); then In progress and Ended, and the archived ones folded at the end. Its heading counts what waits for you (`3 decisions · 1 terminal prompt · 2 finished turns wait for you.`), and a tile opens its task's page. **Next decision** in the top bar, with how many decisions wait, opens the first task in the Wall's order that waits for one; from a task page whose decision is open it opens the one after it instead, round to the start, so going on without answering reaches each, and its count leaves the open task out. **D** does the same from anywhere; with no other decision waiting the button is gone. The **task page** (`/s/<id>`) fills the window under the top bar (a narrow window whole), with the Wall kept as it was under it, also when the page was loaded on its own, and has the tabs Overview, Conversation, Diff, Artifacts, Documents and Architecture, the task's `⋯` menu, and its name: the Claude session's name (Claude's `/rename` or its generated title), which a click renames in both. A running session gets `/rename` typed into its terminal (it runs even mid-turn); an ended one gets a `custom-title` line in its transcript. Esc, the back button or **Wall** returns to the Wall, also after going from task to task by Next decision. Overview shows, top to bottom: what Claude is doing now (the tool and what it is doing, read from the transcript, how long the turn has run, and on a line under it your message that it is answering), while a decision is open Claude's latest reply, so what you decide on comes first, then the decision (see **Decisions**), the **Terminal** button of a task that needs focus, or the reply box, Claude's latest reply here when no decision is open (always whole, under your prompt it answers, which is cut to three lines until **Show all**; what it wrote after its last tool call, with the text before a question or menu, so the progress notes between tool calls stay out; the turn before shows until the current one has such text, headed Claude's previous reply meanwhile), under it **Your latest message** from the moment you send it until Claude replies to it (counting down with its **Undo** while the send is held, then Sent, Queued while a message sent mid-turn waits for Claude's current step to end, and what Claude is doing about it), then the facts (the repository, the worktree's name, or None for a task in the main checkout or one whose worktree was removed, its path with `~` for your home folder, its branch, how much of the context window the conversation fills (a share with a gauge that runs from green through amber to red, the tokens on hover; the tokens Claude's latest request sent, read from the transcript; a 1M window for a Claude 5 model, a model picked by its bare alias, a `[1m]` model or past 200k tokens, 200k for an older one) and the session id; the path, branch and session id copy on a click, the path whole), the **Links** Claude gave in its messages and questions, newest first and kept after they scroll out of the transcript (each described in a few words by `claude -p --model haiku`, or by its host and path until then), and its **Earlier conversations**. A link to another site, there or in any reply, opens in your default browser (the server runs `open`), never in the board's window. While you type in a reply box or New task, nothing that would take the field away changes until you leave it. The browser tab's title is `Pitwall`, and the pill beside the name says whether the board is **Live** or **Reconnecting…** (answers sent meanwhile wait and go out once it is back). When a long reply pushes the open decision out of view, **Decision waiting below** (or Question, or Questions) shows at the top of Overview and scrolls to it.
- **Decisions**: a task's Overview answers its open decision in place, under a line that names its kind (Decision, Asked in the terminal, Questions), Claude's category for an `ask_human` question and how long ago it was asked: the question, Claude's details (Space hides them), the options with what each does, numbered in Claude's order, and a reply box; a menu shows its questions with their options, a round its questions (see **Rounds of questions**). The main button names what ⏎ sends: the option Claude recommends, with what you wrote in the reply box, the picks of a menu or the answers of a round; with none of these it waits for a pick, or goes to the reply box on a question without options. An option, or a pick in a menu of one single-choice question, sends at once. **Dismiss** clears a question or a round unanswered, **Decline** a menu. A question Claude asks in plain text at the end of its turn is no decision: the task is Your turn, with Claude's latest reply and the reply box. For 0.9 s after a decision comes up or changes, the keys and buttons that answer it do nothing. Once you answer, the decision leaves the page and, while another task waits for a decision, **Next decision** shows in its place.
- **Tooltips**: every hint on the board, from a button's what-it-does to a tile's clock or a usage window's reading, shows in one translucent tooltip, a moment after the pointer rests on it (a mouse or pen; a touch shows none) or as soon as it has keyboard focus, also on a disabled button, which says why it is disabled. It sits above the element, or below it when there is no room, and inside the window, over the task page and its dialogs too. Scrolling, a click or leaving the element takes it away, and Esc with one showing dismisses only the tooltip. While it shows, the element is described by it for a screen reader. An action that sends text to a Claude, where its button does not say which Claude or what it knows, explains itself in three parts: what it does, what that Claude has in its context and which session it is. That covers Later and Ask on the side, Send comments in Documents and the next steps, Continue the turn, Try again, Resume, Pause and Resume all (each quoting the prompt it sends), and the bug report's File and fix.
- **Keys** (**?** lists them): on a task page's open decision, ⏎ does what the main button says, Space shows or hides Claude's details and W goes to the reply box; options are pressed, as the digits pick the tab there. D opens the next task that waits for a decision, Z takes back the last send while it waits, N opens New task, B the bug report, and Esc takes back a send that waits, then closes what is open, then goes back to the Wall. On a task page, 1 to 6 pick the tab, and J and K step through the diff's files.
- **Artifacts**: `pnpm claude:connect` also allows the `create_artifact` tool on the same MCP server. A Claude calls it when it decides a picture explains something better than prose (a flow, a before/after, a state machine, a timeline, a comparison): a title and one self-contained HTML document of at most 100,000 characters. As with `ask_human`, the tool only acknowledges; Pitwall reads the call from the transcript and saves the HTML under the session's folder in the app's state, so it outlives the transcript window it was read from. A later artifact with the same title is its next version: every version is kept, with no limit on their number, numbered v1, v2, … in the order they came (an artifact stored before versions were kept is v1 of its title). A task that has any gets an **Artifacts** tab on its page (and links in Overview) that lists each title once, with its latest version, and shows it in a sandboxed frame; **Open in new tab** shows one alone. Beside the title a picker (`v3 v2 v1`, a menu past four) shows an older version in the same frame, under its own URL, and **Changes** shows what the version says differently from the one before: the server reads the visible text of both pages (scripts, styles and comments left out, one line a block, nothing run) and the tab shows a diff of their lines with the words changed marked. Clearing or forgetting a task removes every version with its folder. They are served with a CSP that allows only inline script, style, `data:` images and fonts and makes their origin opaque, so an artifact can neither load anything nor call Pitwall.
- **RPI workflow**: New task's **More** has **Workflow**, None or **RPI**, kept for the next task like its other choices. RPI starts Claude on [HumanLayer's rpi skill](https://github.com/humanlayer/skills) (the `rpi` plugin, which `pnpm claude:connect` installs) with the prompt as one command whose first line names the task directory: `/rpi:rpi Add CSV export; task directory: .pitwall/artifacts/csv-export`, the rest of the prompt and any attached files on the lines after it. The board invokes the skill as `/rpi` when Claude Code lists a command or skill named `rpi` for the checkout, and else by the name its plugin gives it, `/rpi:rpi`, which is how Claude Code lists a plugin's skill; a `/rpi …` you type is a command either way. The directory is the branch with `/` as `-` (the task's name for a task across a folder of repos), relative to where Claude starts. rpi keeps its work there as Markdown documents (`NN-request-…`, `NN-research-questions-…`, `NN-research-…`, `NN-design-discussion-…`, `NN-prd-…`, `NN-tdd-…`, `NN-structure-outline-…`, each with a `type:` in its front matter) with HTML mockups and diagrams beside them. These are never committed: each checkout has one `.pitwall/` folder, and starting an RPI task adds `.pitwall/` once to the repository's own `.git/info/exclude`, which its worktrees share (`.gitignore` is never touched), so they stay out of git and the Diff; a task across a folder of repos keeps them in its task folder, outside every repository. A task has a workflow when such documents exist, however they got there: Pitwall reads every folder under `.pitwall/artifacts/` of the task's worktree (of a task across a folder of repos, its task folder and the worktrees it opened) at each sync, reading again only a document whose time or size changed. Such a task gets a **Documents** tab (5): its documents in workflow order with their type, the selected one drawn as Markdown, its Mermaid diagrams drawn too (Mermaid loads only for a document that has one, from the board itself), its pictures shown, a link to another document opening that one in the tab and a link to a mockup the mockup, in the same sandboxed frame as an artifact; it opens on the document of the phase under way and shows a change on disk within a sync, where you were reading. The board keeps every version of each document, with no limit on their number, in its state folder (`sessions/<task>/documents/`, never in the worktree), and they go when the task's folder does, as its artifacts do. A version is cut once the document's text differs from the last version kept, has stood unchanged for 2 s and the task's Claude is not in a turn, so a turn that writes a document in several steps makes one version and a file touched without a change makes none; until then the document reads as the version it is about to become. The list shows a document's version once it has more than one (`v3`), and the document's heading shows it with a picker (`v3 v2 v1`, a menu past four) that reads an older version in place, read only, under its own URL (`?v=2`). **Changes** shows what changed in the version shown from the one before (the latest from the one before it at first), the Markdown's lines with the words changed in them marked, as the Diff tab draws them. A document that has a newer version than the one you last had open in this browser is marked **Changed since you read it** in the list, and opening it opens on its Changes, so after **Send N comments** you see what Claude changed; one you never opened here is not marked. Overview and Documents show the workflow's phases (questions, research, the design steps of the flow the research questions named: design discussion, PRD then TDD, TDD, or none for research only, the outline, implementation), each done, under way or not yet, or skipped when a later one has a document and it has none, read from the documents alone: the furthest phase with a document is under way, and once the outline's Implementation Overview has a phase checked or marked ✅ implementation is, counted as `Implement 1/3`; with every phase checked the workflow is done. A phase with a document opens it. The Wall's tile names the phase under way in a chip, `RPI · Research`. Reading sends nothing to Claude; what Documents sends, it sends only when you press it:
  - **Comments**: selecting text in the shown document offers **Comment** by the selection, a box for what should change: Enter (or **Keep for later**) keeps it under Later and **Send when it's my turn** arms it, as a line draft of the Diff; Esc drops it. A comment keeps the document's path, the nearest heading above the passage, the passage itself (at most 600 characters, cut with `…`) and the version it was written on: comments can be written on an older version too. In the document each passage commented is marked in the version it was written on only (a comment from before versions, in the latest), with the comment on hover, and the list counts each document's comments (`2 comments`). Under Later a comment shows the document and heading over the passage, with its version once the document has more than one (`v2, now v3` when it is no longer the latest), and a click opens the document, in that version, at it, marked; a comment whose passage no longer occurs stays under Later unmarked and opens at its heading, and one whose document is gone says so. Sent on its own from Later, a comment reads ``About `<path>`, under “<heading>”:`` with the passage in `>` lines, then the comment. One written on a version that is no longer the latest says so after the heading, `(written on version 2; the document is at version 3 now, so the passage may have moved)`, here and in **Send N comments**.
  - **The board moves the phases**: what the board sends rpi, the first prompt, the comments and the next steps, ends with one line telling it that Pitwall starts each next phase from its buttons in a new conversation, so rpi ends a phase with what to review rather than a command to run in a new session. The board leaves that line out wherever it shows a prompt.
  - **Send N comments**, over a document that has comments, sends them as one message, held for 5 s with Undo like any send, and they leave Later once it went out: `/rpi:rpi update <path>` on the first line, then for each comment `Under “<heading>”:`, the passage in `>` lines and the comment, so rpi updates that document from them.
  - **Next steps**: beside the phase strip, Overview and Documents offer the steps rpi's workflow allows from the phase under way, the flow's usual one first, each sending the command rpi's own handoff gives, for the task's folder: after the research questions **Research** (`/rpi:rpi research .pitwall/artifacts/csv-export; flow: prd`); after the research the flow's design step (**Design discussion**, **PRD** or **TDD**; with no flow named, each of them), **Outline** and **Implement**, each with the flow; after a PRD **TDD** (`; flow: prd`), **Outline** and **Implement**; after a design discussion or a TDD **Outline** and **Implement**; after the outline **Implement**, and while implementing **Implement the next phase** (`/rpi:rpi implement <folder>`). Every step starts a new conversation, as rpi runs each phase in a context of its own: `/clear` goes first and the command is typed once the board has seen the new conversation `/clear` started, with nothing else typed between the two; when the `/clear` fails or no new conversation starts within 15 s the command is not sent and the send is marked **Not sent**. With comments not yet sent on the document of the phase under way, the steps say so (`2 comments not sent`) without holding them back.
  - Both go only at the end of a turn: while Claude works, shows a question in its terminal or has ended, the buttons are disabled and say why.
- **Architecture**: a task can show its repository's architecture as an interactive diagram, drawn from a [LikeC4](https://likec4.dev) model: the `.c4` files directly in `.pitwall/architecture/` of its checkout, which git ignores as the rest of `.pitwall/` (a checkout seen with a model gets `.pitwall/` in the repository's `.git/info/exclude`). The repository's main checkout holds the project's model; a worktree the board creates for a task, or `open_worktree` opens, starts with a copy of it unless it has a model already, and the task's Claude changes that copy. `pnpm claude:connect` copies the **architecture** skill (`config/skills/architecture`) to `~/.claude/skills`: `/architecture` has Claude read the code and write or update the model (the context, the containers, their components, and a diagram of each element that has parts), `/architecture <change>` has it model what the task changes, and Claude checks the model with `node <pitwall>/scripts/architecture.ts check`, which lays it out as the board does, without the network. A task whose checkout has a model gets an **Architecture** tab (6). The server lays a model out with LikeC4 only when the tab asks for it (LikeC4 loads then, not at start), once for each content of its files, kept in memory; a sync only lists the files and reads one whose time or size changed. The tab draws the model on LikeC4's canvas, which loads with the tab from the board itself, in the board's light or dark and its font, with nothing from any other host (no fonts, no icons): drag to pan, scroll or pinch to zoom, a click on an element opens its details (description, technology, links, relationships), the magnifier on an element goes into its diagram, the trail above the canvas leads back up and the picker to any diagram. The diagram is in the URL (`?view=api`), so Back steps out of it and a reload keeps it. A model that does not parse shows LikeC4's errors instead, each with its file, line and column. **This task's changes** (`?changes`) compares the task's model with the main checkout's, elements by id and relationships by source, target, kind and title: the canvas draws what the task adds green and what it changes amber, and a list names what it adds, changes and removes. While the two differ and the task's model has no errors, **Keep as the project's architecture…** asks first, naming the main checkout's folder and the changes, then puts the task's `.c4` files in place of the main checkout's (only those, and never through a symlink), and its toast's **Undo** puts the earlier ones back, for 10 minutes and unless the project's model changed meanwhile. A task across a folder of repos has a model in each worktree it opened, picked above the canvas.
- **Claude Code's own questions** (`AskUserQuestion`) show as a decision too: the questions side by side, each with its options, numbered across them, multiple choice where allowed, and your own answer on single-choice questions. `pnpm claude:connect` installs a `PreToolUse` hook on `AskUserQuestion` that only posts the questions to Pitwall and never answers them, so the terminal menu still opens. The decision clears when the transcript has the answer (the call's `tool_result`), or when the session goes idle or ends. **Send answer** drives that terminal menu with named keys (arrows, Enter, Tab), never digits, which a non-US keyboard layout would turn into other characters. A menu answered from the board that is still open 10 s later turns into Needs focus: Claude still shows it in the terminal.
- **Rounds of questions**: when Claude has several separate questions at once, as in an interview about a plan, it calls the `ask_questions` tool (same MCP server, allowed by `pnpm claude:connect`) with each question's title, body, options and its recommended answer. The round is one decision: its task page shows every question on its own, answered right there by an option, by **Take it** on Claude's recommendation, or by an own answer, which also goes along as a note with a pick. **Take every recommendation** answers what is still open and has one. The answers are a draft kept in the browser (localStorage), so they outlive a reload or a closed window. **Discuss** on a question talks it through before you answer: it is Ask on the side scoped to that question, a read-only fork of the conversation that knows the plan and every question, shown under the question with follow-ups, and **Use as my answer** copies what it said into your own answer; the task's Claude never sees it, and it goes when the round does. The main button counts the answers ("Send 3 of 7 answers") and sends them as one message, each named by its number, after the usual 5 s Undo; a question left out is said to be still open, so Claude asks it again. The reply box under the questions (W) sends a message of your own in place of answers, and **Dismiss** clears the round. `pnpm claude:connect` also copies the **grill-me** skill (`config/skills/grill-me`) to `~/.claude/skills`, so `/grill-me` or "grill me on …" in any session interviews you in rounds posted this way; a folder of that name that is your own is left alone. A round that a session wrote as text in that skill's format (`❓ **Q1** - **title**: …`, `➡️ recommendation`, a rule between questions, choices lettered `- (a) …`) is read from the transcript without a model and shows the same way.
- **Reply box**: Enter sends, Shift+Enter adds a line. On a decision W goes to it: Enter answers with what you wrote, and an option pressed takes your text along as a note. Text starting with `/` or `!` is typed into the session as is, so slash commands and skills work and an open question stays open (a plugin's command or skill counts by its bare name too, `/rpi` for `rpi:rpi`); typing `/` suggests your built-in, user, project and plugin commands and skills (Tab or Enter completes). The box grows with its text. Paste or drop files into it: they are saved under `~/Library/Caches/pitwall/uploads` (kept 30 days) and sent with the message. Images go in as a paste of their own, which Claude Code turns into `[Image #N]` attachments; any other file goes in as its path for Claude to read.
- **Only the decision you saw**: an answer and **Dismiss** name the decision the page showed. When that is no longer the open one (answered in the terminal, replaced by a newer one, or Claude moved on), nothing is typed or changed: a toast says why, the page catches up, and your draft and attachments stay in the reply box. A message sent while the page showed no decision is held back the same way when Claude has asked something meanwhile. `/` and `!` commands are not answers and are never held back for this. Every send waits 5 s before it goes out: the decision leaves its page, and a toast counts down with **Undo** (or Z, or Esc), which brings it back with what the send took from the reply box. A command waits the same way but leaves the decision open, and Archive is not held: its toast's Undo unarchives. Closing or reloading the window sends what is waiting at once; one that never reached the board comes back on the page after it, marked **Not sent**, with what it took from the reply box. The server takes the first answer to a decision and closes the decision at once, so a second one, from another window say, is refused; a send it refused comes back on its task's page, marked **Not sent**, and the toast's **Show** opens that page.
- **Conversation** (the task page's third tab, or 3): the task's whole conversation, oldest first, opened at your last prompt: each of your prompts, with the pictures pasted into it (a click shows one larger), and Claude's reply to it, which is what it wrote after its last tool call, as in the latest reply, so the steps between stay out, with the artifacts it made meanwhile (a click opens one in Artifacts). Commands, background-task notices and `/compact` summaries are not prompts; a turn that ended on a tool call (interrupted, or still working) shows no reply. Conversations the task had before a `/clear` come first. A copy button in the heading of each prompt and reply, shown when you point at it, copies its text as written (a reply as its Markdown); Claude's latest reply has one too, in Overview. The transcript is read when the tab opens and again after each new reply, never in the background, and each picture only when it comes into view.
- **Open in Finder / Open in VS Code** (the `⋯` menu of a tile or the task page): opens the task's worktree folder. **Open in Ghostty** opens a new tab with a plain shell in the folder Claude runs in, apart from Claude's own terminal.
- **Clear task** (`⋯` menu): asks first, naming the branch, the path and what would be lost; then quits every Claude running in the task's worktree, closes the Ghostty tabs in it, removes it with `git wt rm --force`, deletes its local branch, except the base branch and long-lived ones (`master`, `main`, `develop`, `trunk`, `release/*`), and removes the task from the board with its data. A task in the repository's main checkout keeps the checkout and its branch: only its own Claude quits and its tab closes, as other Claudes may share the checkout. **Remove** in the Repos dialog does the same, but keeps the branch unless asked and refuses a worktree with changes unless Force is ticked. Both refuse when another worktree sits inside this one.
- **Later**: a task's Overview has a **Later** box for messages you think of while Claude works and want to send yourself later, so nothing reaches Claude mid-turn. Enter keeps one as a draft (Shift+Enter breaks the line); the drafts are stored on the board, so a reload or another window has them too, and the task's Wall tile counts them (`Later 2`). Each draft has **Send now**, held for 5 s with Undo like any send, **Edit** and **Delete** (with Undo); with two or more, **Send all now** sends them as one message. A draft with **Send when it's my turn** ticked goes by itself when Claude ends its turn and leaves the list once it went out. With several ticked, one goes at each end, in the order of the list, so each starts a turn of its own and the next waits for the end of that turn. It goes only at a real end of a turn the board saw (working, then your turn; a permission prompt or a menu is not one). It does not go when you replied on the board after that end, Claude started working again, or the task is paused, being paused, archived, cut short by a restart or stopped on an error, nor when the turn ended on a question, which the draft would answer by accident: an `ask_human` question, a round or a menu, or a reply whose last paragraph ends on a question mark (closing `*`, `_`, `` ` ``, quotes and brackets after it count too); it then waits for the next end. Ticking it counts from that moment, so a turn that had already ended does not send it.
- **Ask on the side**: the Later box's other button, beside Keep for later, asks what you wrote as a question you want answered without interrupting the task, instead of keeping it as a draft (Enter keeps it). Pitwall forks the task's conversation as it stands (`claude -p --resume <id> --fork-session`) and the fork answers it, knowing everything the task knew up to then, while the task's Claude goes on and never sees the question. The fork runs on the model and effort picked beside the button, the first being the task's own (the next question starts on the same pick, its follow-ups run on it and its card names it; a draft kept for later always goes to the task's Claude on its own model, as typing /model into it would also change your default for new sessions), reads files and the web (Read, Grep, Glob, WebFetch, WebSearch) but cannot edit or run anything, as it shares the worktree, and runs without MCP servers or hooks. While it answers, the aside shows what it reads, with **Stop**. A follow-up under an answer goes to the same fork, resumed by its session id. **Keep as a draft** puts the last answer under Later, to tell the task's Claude when you decide, and **Close** forgets the aside and deletes the fork's transcript; clearing or forgetting the task deletes its asides' forks too. Every action in the Later box, its drafts and its asides explains itself on hover or keyboard focus: what it does, what the Claude it reaches has in its context (the task's whole conversation, a copy of it as it stood, or nothing until you send), and whether that is the task's own session or a separate fork. A task keeps up to 10 asides; one answering when Pitwall restarts says it got no answer and takes the question again.
- **Archive is done, not running**: archiving a task quits its Claude, and a Claude still at work first finishes its turn; an archived task never keeps a Claude running, so a conversation resumed by hand (`claude --resume`) brings its task back. The conversation stays: **Unarchive**, the toast's Undo and **Continue** resume it in a hidden terminal, once a Claude still quitting has gone. **Clear task** quits every Claude in the task and removes its worktree.
- **/clear and /resume**: a task is not its conversation. `/clear` in a task's Claude starts a new conversation that takes the task over: its name, artifacts and links stay, an open task page stays on it, and the old conversation is listed under **Earlier conversations** with its id for `claude --resume`. Only a conversation that `/clear` started takes a task over. A `/resume` into a conversation a task ran brings that task back, and into any other starts a task of its own; either way the task it left ends and is archived. While a task runs another conversation, one of its earlier conversations opened elsewhere (by `/resume` in another task or `claude --resume`) does not bring it back but starts a task of its own, and the task keeps the conversation it runs.
- **Pause**: before you close the laptop or restart the Mac, **Pause** in the top bar (not in a phone-sized window) brings every Claude at work to a stop. Each one finishes its turn, then gets a short prompt asking it to stop its own background tasks (shells, watchers, monitors, agents) and end its turn; a Claude with only background work running gets that prompt at once. A turn that starts meanwhile, from a message you send too, is waited on as well. The banner names the tasks still finishing a turn and how long the longest has run; **Stop now** sends Esc to those. A task is paused once it is idle with nothing in the background, and its tile reads **Paused**; once all are, the banner and a macOS notification say it is safe to close the laptop or restart. **Resume all**, or **Resume** on a task page, asks each one to start its background tasks again and carry on, relaunching one whose Claude ended meanwhile, by a restart too. **Cancel** stops pausing and leaves stopped what has stopped; **Dismiss** forgets the pause. After a restart that also ended other tasks, the paused ones show in the restart's banner instead (see below).
- **Restarting the Mac**: a restart ends every Claude with it, hidden or not. On its first look after the boot, the board tells the tasks the restart ended (any it had last seen running before the boot, by `sysctl kern.boottime`) from those that ended on their own, and keeps what each was doing: working, your turn, a decision, or a prompt in the terminal. A banner under the top bar counts them ("ended 2 tasks"), and their tiles read **Ended by restart**. **Resume all** continues each one in a hidden terminal (`claude --resume`, as Continue does), and a toast names any it could not, which stays ended. A task that was only waiting for you comes back as it was. One cut short mid-turn, or at a prompt the restart closed (no tool call it asked for ever ran), says so on its page and in the banner until Claude works again: **Continue the turn** sends Claude a message asking it to check where it got to and carry on, held for 5 s like any send. Nothing is continued by itself. **Dismiss** forgets it all, and ended tasks stay on the Wall with Continue. Archiving an ended task forgets the restart for it too: unarchived later, it is an ended task like any other, with Continue, and the banner does not come back for it. Tasks you paused before the restart keep their **Paused** label. When the restart also ended other tasks, one banner covers both groups: it counts the ended ones by what they were doing, names the paused ones, and its one **Resume all** has each paused task start its background tasks again and carry on, and brings the others back as they were. A toast names any task it could not resume; that task stays ended, and a paused one stays paused. Its **Dismiss** forgets both. With only one of the two groups, the banner is the pause's or the restart's own, as described here. Before a restart you plan, use **Pause**.
- **PR to green**: when a session uses the `pr-to-green` skill, its tile and its task page show the PR (linked) and the last result of `watch-pr.sh`: checks running, green, failed (or fixing while the session works on it), merged; the chip's dot pulses while the watcher runs.
- **Usage limits**: the top bar always shows how much of the plan's 5-hour and weekly limits is used (`5h 34%`, `7d 61%`; amber from 50 %, red from 80 %), with the reset time and the time of the reading on hover. A tick on each bar marks an even pace, the share that would be used by now if the window were spent evenly until its reset (the part of the window already gone), and the hover says how far over or under it you are; below 1300 px the bars give way to the shares and only the hover tells the pace. A window whose reset time has passed shows 0 % until the next reading. Every Claude's status line replaces the copy, and Claude Code leaves out a window whose reset has passed since that Claude's last reply, so a copy without a window keeps that window's last reading instead of showing `–`. Claude Code gives these numbers only to the status line, so your status line script (which gets Claude Code's JSON in `$input`) copies them for the board with the lines below; until it has, both show `–`.
- **Claude Code's undocumented files**: Pitwall reads each running Claude's `~/.claude/sessions/<pid>.json` and the JSONL transcripts, which Claude Code does not document. `pnpm claude:connect` also installs `SessionStart`, `UserPromptSubmit`, `Stop` and `Notification` hooks that only post to Pitwall: each event syncs the board at once (the 1.5 s poll stays, to catch what no hook reports, such as a crash), and the hooks tell where a conversation's transcript is and whether `/clear` started it, so for those sessions the board neither guesses the project folder's name nor looks for the `/clear` marker. When a session file or transcript lacks a field Pitwall relies on, or a hook's transcript path differs from the folder Pitwall would guess, a banner names the Claude Code version and what changed. `server/fixtures/claude-<version>/` holds what one version wrote, blanked, and the tests read each; `node scripts/fixture.ts <transcript.jsonl> <sessions/pid.json>` captures a new version.

  ```sh
  usage="$HOME/Library/Application Support/pitwall/usage.json"
  jq -ec '{at: (now * 1000 | floor), rate_limits} | select(.rate_limits)' <<<"$input" > "$usage.$$" 2>/dev/null && mv -f "$usage.$$" "$usage" || rm -f "$usage.$$"
  ```
- **Stopped on an error**: a turn that ends on an API error instead of a reply marks its task **Stopped on an error**, and its page says what to do for the kind of error: a message the model's safeguards flagged is rephrased, a usage limit or a failed request gets **Try again**, an expired login needs /login in the terminal. When only the model in use is out of usage (Claude Code's "out of usage credits … or /model to switch models"), **Continue on Opus**, **Sonnet** or **Haiku** (the ones it was not on) types `/model <name>` into the session and then asks Claude to answer your last message again, each held for 5 s with Undo.
- **Usage log**: to tell what to improve, the board records how it is used. The page records time on each screen, the board keys pressed (and keys that did nothing or that the board has no use for), the controls clicked, the decisions shown, sends and their Undo, the New task dialog's choices, dialogs, slow responses (input to the next paint over 200 ms), freezes, crashes, lost connections and reloads, each with how many tasks were open. The server records each decision opening and closing, answered on the board (how: option, own text, menu, round, dismiss) or elsewhere, and each task starting and ending. It never records what is typed or what a task, question, option or answer says: task names read as `task`, and the server drops content fields from every event. It stays on this Mac in `state.db` (table `ux_events`, kept 180 days). `pnpm ux` reports the last 30 days (`--days 7`), with the saved queries in [`scripts/ux/`](scripts/ux) (waiting and decision time, how decisions end, Undo rate, tasks, New task, slowness, waiting by load, what was read before acting); `--json` gives the raw events, e.g. for Claude to look for patterns.

## Run

```sh
pnpm install
pnpm build              # UI → web/dist
pnpm service:install    # launchd agent: starts at login, restarts on crash
pnpm claude:connect     # ask_human MCP server, hooks, grill-me, architecture and the rpi plugin for all Claude sessions
pnpm open               # Brave Beta --app window on http://127.0.0.1:7420
```

`pnpm claude:connect` adds HumanLayer's plugin marketplace (`claude plugin marketplace add humanlayer/skills`) and installs its `rpi` plugin for your user (`claude plugin install rpi@skills`), each only when it is not there yet; a marketplace of yours named `skills` from elsewhere is left alone, and a failure is reported without stopping the rest of connect. `pnpm claude:disconnect` leaves the plugin installed. Connect also copies the skills `grill-me` and `architecture` to `~/.claude/skills`, the latter with this checkout's path in its check command (so connect again after moving Pitwall), leaving alone a folder of either name that is your own; disconnect removes the copies.

Pitwall was called Agent Board. `pnpm service:install` removes the old `dev.agent-board` agent and moves its state and uploads to Pitwall's folders, and `pnpm claude:connect` replaces the old MCP server, keeping its tool permissions for the sessions that still use it (`pnpm claude:disconnect` removes them). Sessions started under the old name keep working: their `ask_human` and `create_artifact` calls still count, and hidden ones stay on the old tmux socket until they end. A status line script that copies the usage limits needs the new path above.

Code changes never restart the server on their own. A UI-only change needs just `pnpm build`: open pages reload into it within about 4 s, once the server has read the new `index.html` twice, 2 s apart (a page waits while you type in it, have a dialog or menu open or a send is on its way; after 15 s the top bar offers **New version · Reload** instead). After pulling or editing server code, run `pnpm build` (UI) and `pnpm service:restart`; Claude sessions keep running either way. Re-run `pnpm service:install` after switching Node versions, since the agent pins the current `node` path.

Development: `pnpm start` runs the server in the foreground (stop the launchd agent first with `pnpm service:uninstall`), `pnpm dev` serves the UI with HMR on :5173, `pnpm check` typechecks, lints and runs the tests (`pnpm test` runs only the tests: transcript parsing, schedules' timing, artifact storage, decisions and answering them, drafts sent at the end of a turn, menu keystrokes, the UI-build watcher, the diff, `git wt` and tasks across a folder of repos on throwaway repos, the Wall's order, the next decision and the clocks, what a decision's buttons send, held sends and keys, rpi's documents and their phases, comments on them and the messages they make, the versions of documents and artifacts and when a document's is cut, the visible text of an artifact, the migration of stored artifacts, rpi's next steps for every flow, how `/rpi` is invoked, `/clear` before a command, which files the documents' routes may read, the exclude file and connect's plugin install, the architecture model: where it is found, its summary, the layout cache, the comparison, the copy into a new worktree, Keep and its path safety, the skills connect copies and the skill's example). The tests run with `HOME` set to a fresh temporary folder and `TMPDIR` to a folder inside it, so none of them can reach the live board's state and nothing they make outlasts the run.

To try UI changes away from the live board (where one key answers a real session), `pnpm mock` serves the built UI against made-up sessions on :7421 (`--scenario volume`, `--scenario workflow` for tasks with rpi documents on disk, a comment on one, and a document and an artifact with three versions each, `--scenario architecture` for a repository with a model, a task that changes it and one whose copy does not parse, `--port`; `GET /mock` lists the scenarios) and answers them by the server's own rules, and `PITWALL_API=http://127.0.0.1:7421 pnpm dev` points the dev server at it; without that variable `pnpm dev` talks to the live board. `pnpm mock --legacy` answers like a server from before the `answered` record (none in the snapshot, no refusal codes) and names the UI build only when a socket opens, to check a UI against one with `pnpm e2e --port <its port>`. `pnpm e2e` drives the built UI through scripted checks in headless Brave windows of their own, each worker against a mock of its own (`--workers <n>`, by default half the cores, at most 6): every check runs once at 1440×900 or narrow at 390×844, in dark, and checks colours and contrast, and takes its screenshots, in light too by switching the system's scheme while it runs. Checks that only wait out the page's timers (the 5 s hold of a send, the 0.9 s guard) run on a clock four times faster; a few keep real time so the timers themselves stay covered. `--only <pattern>` picks checks, which is the way to work while changing something; `--matrix` runs every check in each scheme, adds 1100×900 and reduced motion; a failure leaves a screenshot in `.e2e/`. A check fails on an error in the page and on a request to any host but 127.0.0.1, and one that hangs fails after 60 s without holding up the others. `--dist <dir>` checks a build of your own (`pnpm exec vite build --outDir <dir> --emptyOutDir`); a build older than the UI's sources is refused (`--stale` checks it anyway). The mock runs with `HOME` set to a fresh temporary folder, and every path it shows lies in it.

State lives in `~/Library/Application Support/pitwall/` (`state.db`, per-session hook/MCP config, artifacts and document versions under `sessions/<task>/`, `server.log`, and `brave/`, the browser profile of the board's window).

The board's window runs in Brave Beta, not Brave. Installed from Brave it shares Brave's process, so quitting Brave closes the board; with only a profile of its own it is still Brave to macOS, and opening Brave while the board alone runs lands in the board's profile.

## Notes

- Needs tmux and Ghostty 1.3+ (AppleScript), and macOS Automation permission for the server to control Ghostty; no screen recording. Node's hardened runtime cannot hold that permission, so `pnpm service:install` builds a small launcher (`scripts/launcher/launcher.c`, ad-hoc signed with the Apple Events entitlement, in Pitwall's Application Support folder) that launchd starts and that runs the server as its child. macOS asks once to let **pitwall** control Ghostty; the launcher is rebuilt only when its source changes, since a rebuilt one has to be allowed again.
- Brand-new folders trigger Claude's "trust this folder" prompt once. Claude registers itself only after it, so a hidden session shows as waiting on its start-up prompt; answer it through **Terminal**.
- A Claude running in another terminal app or in your own tmux still shows up, but Terminal and answering need it to be a hidden session or the foreground process of a Ghostty tab.
- Light/dark follows the system until the top bar's theme button picks Light or Dark; the choice is kept in that browser, and System follows the system again.
